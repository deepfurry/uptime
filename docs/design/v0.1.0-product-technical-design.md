# DeepFurry Uptime v0.1.0 产品与技术设计

> Status: Design Baseline  
> Target version: v0.1.0  
> Date: 2026-09-16  
> Working product name: DeepFurry Uptime  
> Working repository: `deepfurry/uptime`（仓库名可在 bootstrap 阶段最终确认，不影响本文技术契约）

---

## 1. 文档目的

本文定义 DeepFurry Uptime v0.1.0 的产品边界、技术架构、配置契约、存储语义、生命周期、CLI、发行与运维行为。

本文不是详细编码任务书。实现阶段可以调整内部文件拆分、私有函数和测试组织，但不得在没有重新评审的情况下改变本文定义的产品行为、公开配置语义、公开 `storage/bbolt` 契约或数据安全边界。

v0.1.0 的目标不是构建完整监控平台，而是交付一个可以长期维护、开箱即用、轻依赖、行为可预测的 Uptime 小产品。

---

## 2. 产品定义

DeepFurry Uptime 是一个基于 Fiber v3 与 Fiber Contrib Uptime 的轻量自托管 Uptime 服务。

核心体验：

> One binary. One config. Zero external infrastructure by default.

用户只需要一个可执行文件、一份 YAML 配置，以及默认自动创建的 bbolt 数据文件，即可获得：

- HTTP/HTTPS Endpoint 可用性探测；
- 历史可用率与日级状态；
- Fiber Uptime 内置状态页；
- JSON 状态 API；
- 本地 bbolt 持久化；
- 可选 Redis 外置持久化；
- 可选静态 TLS；
- 可选 Basic Auth；
- `/livez` 与 `/readyz`；
- 历史 Service 的显式导出与删除；
- Binary / Docker / systemd 示例部署。

DeepFurry Uptime 是 **standalone product**，而 Fiber Contrib Uptime 是它依赖的 **engine / middleware**。

---

## 3. 产品目标

### 3.1 主要目标

1. 默认零外部中间件依赖。
2. 单 binary 即可运行。
3. 配置文件即主要管理界面，不建设后台管理系统。
4. 尽量直接采用 Fiber 官方生态能力。
5. 默认部署、升级、备份和故障行为简单、明确。
6. bbolt backend 同时作为可复用的公开 Go package 提供给其他 Fiber Uptime 用户。
7. 历史数据删除必须显式发生，配置变更不得自动销毁历史。
8. 被监控服务故障与 Uptime 自身故障必须严格区分。

### 3.2 非目标

v0.1.0 明确不做：

- Prometheus / Grafana 替代；
- APM、Tracing、日志聚合；
- ICMP / DNS / TCP / TLS Certificate 独立探针；
- Email、SMS、Webhook、PagerDuty 等告警系统；
- Incident Management / On-call；
- 用户数据库、RBAC、多用户系统；
- OAuth / OIDC / GitHub Login；
- 管理后台；
- PostgreSQL / MySQL；
- 分布式 probe scheduler；
- leader election；
- Redis 多副本探测去重；
- 配置热重载；
- ACME / AutoCert；
- Archive Import / Restore；
- 在线 bbolt 管理控制面；
- 自定义前端或 React/Vite 构建链。

## 4. 核心设计原则

### 4.1 Fiber-native

优先采用 Fiber 官方能力：

- Fiber v3；
- Fiber Contrib Uptime；
- Fiber Log；
- Fiber Redis Storage；
- Fiber Hooks；
- Fiber BasicAuth；
- Fiber TLS Listen 能力。

除非存在明确产品缺口，否则不再包装一套重复抽象。

### 4.2 Fiber owns the application lifecycle

运行时生命周期围绕 Fiber Hooks 组织。

不新增：

- Lifecycle Manager；
- Worker Supervisor；
- Service Container；
- 第二套 shutdown framework。

Signal handler 只负责触发 Fiber graceful shutdown。

### 4.3 Configuration over administration

YAML 是当前监控配置的唯一 source of truth。

不通过：

- CLI flags；
- 数据库 CRUD；
- 后台管理页面

动态修改产品行为。

环境变量只用于向当前启用配置中的字符串字段注入值，不形成第二套配置结构。

### 4.4 History is explicit

配置控制“现在监控什么”，存储保留“历史发生过什么”。

> Configuration controls observation; storage preserves history; deletion is always explicit.

从 YAML 删除 Endpoint 不会自动删除其历史。

### 4.5 Product config is not a serialized framework config

产品只暴露用户真正需要理解的参数。

不把 Fiber、Redis、bbolt、`crypto/tls` 的所有内部参数机械映射到 YAML。

### 4.6 Fail-fast at boot, degrade at runtime

启动时关键依赖不可用时拒绝启动。

已经成功运行后发生短暂存储故障时保持进程存活，进入 degraded / not-ready，等待底层依赖自然恢复。

## 5. 技术基线

### 5.1 Go

初始最低基线：

```text
Go 1.26
```

项目约定：

> 跟随 Fiber 支持的 Go 版本窗口，不单独维护比 Fiber 更老的 Go 兼容承诺。

这是一个产品仓库，但仓库同时公开 `storage/bbolt` package，因此不人为拆分多 module 来维持不同 Go 基线。

### 5.2 核心依赖

直接依赖尽量控制为：

```text
github.com/gofiber/fiber/v3
github.com/gofiber/contrib/v3/uptime v0.2.0
github.com/gofiber/storage/redis/v3
go.etcd.io/bbolt
go.yaml.in/yaml/v4
```

日志使用：

```text
github.com/gofiber/fiber/v3/log
```

不引入：

```text
Cobra
Viper
Zap
slog（应用层）
Lumberjack
直接 go-redis 依赖（由 Fiber Redis Storage 管理）
```

CLI 子命令使用标准库 `flag.FlagSet` 组织。

### 5.3 时区数据

应用嵌入：

```go
import _ "time/tzdata"
```

确保极简容器或缺少系统 zoneinfo 的环境仍可使用：

```text
UTC
Local
Asia/Tokyo
Asia/Shanghai
...
```

```text
                    uptime.yaml
                        │
                        ▼
               Strict Config Loader
                        │
            Active Env Resolution
                        │
                        ▼
                 Config Validation
                        │
                        ▼
                  Fiber v3 App
        ┌───────────────┼────────────────┐
        │               │                │
     /livez          /readyz       Optional BasicAuth
        │               │                │
        │               │                ▼
        │               │          Fiber Uptime
        │               │         /uptime
        │               │         /uptime/api/status
        │               │                │
        │               │                ▼
        │               │        uptime/storage.Store
        │               │          /            \
        │               │         /              \
        │               │        ▼                ▼
        │               │  DeepFurry bbolt   Fiber Redis
        │               │      backend         Storage
        │               │
        └─────────────── Fiber Hooks ────────────────┐
                                                     │
                                     OnListen / OnPreShutdown
                                               / OnPostShutdown
```

### 6.1 bbolt 路径

Standalone 产品：

```text
DeepFurry Uptime
    ↓
storage/bbolt
    ↓
uptime.Config.Storage
```

第三方应用：

```text
Third-party Fiber App
    ↓
github.com/deepfurry/uptime/storage/bbolt
    ↓
gofiber/contrib/v3/uptime
```

### 6.2 Redis 路径

Standalone 产品直接使用 Fiber 官方 Redis Storage：

```text
DeepFurry Uptime
    ↓
fiber/storage/redis
    ↓
uptime.Config.Store
```

不实现 DeepFurry Redis backend。

## 7. 完整配置契约

推荐的 v0.1.0 示例配置：

```yaml
server:
  address: ":8080"
  shutdown_timeout: 10s

  tls:
    enabled: false
    cert_file: "/etc/uptime/tls/fullchain.pem"
    key_file: "/etc/uptime/tls/privkey.pem"

auth:
  enabled: false

  basic:
    username: "${UPTIME_AUTH_USERNAME}"
    password_hash: "${UPTIME_AUTH_PASSWORD_HASH}"

storage:
  type: bbolt

  bbolt:
    path: "./data/uptime.db"

  redis:
    url: "${UPTIME_REDIS_URL}"
    key_prefix: "fiber:uptime"

uptime:
  interval: 10s
  retention: 90d
  window: 30d
  timezone: UTC

ui:
  path: "/uptime"
  title: "Service Status"
  description: "Current service availability."
  footer: "Powered by DeepFurry Uptime."
  favicon_url: ""

  thresholds:
    green: 0.999
    yellow: 0.99

endpoints:
  - id: website
    name: "Website"
    description: "Main website"
    url: "https://example.com/"
    method: GET
    interval: 30s
    timeout: 5s

  - id: api
    name: "API"
    description: "Public API"
    url: "https://api.example.com/health"
    method: GET
    headers:
      Authorization: "Bearer ${UPTIME_API_TOKEN}"
    expected_status_codes:
      - 200
      - 204
```

YAML 使用 strict decoding：

- 未知字段直接报错；
- 不静默忽略拼写错误；
- 不通过 Viper 做隐式类型转换。

## 8. 环境变量注入

### 8.1 语法

仅支持：

```text
${VAR_NAME}
```

不支持：

```text
$VAR
${VAR:-default}
${VAR?error}
shell expression
```

### 8.2 Active Configuration Resolution

环境变量解析发生在 YAML decode 后，根据当前启用配置进行。

只有实际 active 的字段需要成功解析。

例如：

```yaml
auth:
  enabled: false
  basic:
    username: "${UPTIME_AUTH_USERNAME}"
    password_hash: "${UPTIME_AUTH_PASSWORD_HASH}"
```

当 `auth.enabled=false` 时，即使环境变量不存在也允许启动。

同理：

```yaml
storage:
  type: bbolt
  redis:
    url: "${UPTIME_REDIS_URL}"
```

Redis 未启用时不要求 `UPTIME_REDIS_URL`。

但所有配置中的 Endpoint 都属于 active configuration，因此：

```yaml
headers:
  Authorization: "Bearer ${UPTIME_API_TOKEN}"
```

缺少 `UPTIME_API_TOKEN` 时必须拒绝启动。

### 8.3 Secret 行为

以下内容禁止出现在普通日志、状态页或 Archive：

- BasicAuth verifier；
- Redis 密码 / URL credentials；
- Endpoint Authorization Header；
- 自定义敏感 Header。

## 9. Server 配置

```yaml
server:
  address: ":8080"
  shutdown_timeout: 10s
```

### 9.1 `address`

默认：

```text
:8080
```

支持：

```text
:8080
127.0.0.1:8080
[::1]:8080
```

不拆分为 `ip_address + port + network`。

### 9.2 `shutdown_timeout`

默认：

```text
10s
```

使用 Go duration 语法。

必须大于 0。

该 timeout 限制 graceful shutdown 的最大持续时间。

---

## 10. TLS

```yaml
server:
  tls:
    enabled: false
    cert_file: ""
    key_file: ""
```

### 10.1 行为

`enabled=false`：

- 使用 HTTP；
- `cert_file` / `key_file` 可以预先填写；
- 不因为未启用的证书路径不可用而拒绝启动。

`enabled=true`：

- `cert_file` 必填；
- `key_file` 必填；
- 证书和私钥必须可读取；
- cert/key 必须能够成功组成 TLS key pair；
- 任一步失败都属于 fatal startup error。

严禁：

```text
TLS failure → fallback HTTP
```

用户要求 TLS 时，要么 HTTPS 成功，要么应用不启动。

### 10.2 v0.1.0 不支持

- ACME；
- AutoCert；
- mTLS；
- 自定义 cipher suite；
- YAML 中完整暴露 `tls.Config`。

## 11. 鉴权

v0.1.0 只支持可选 Basic Auth。

```yaml
auth:
  enabled: true
  basic:
    username: "admin"
    password_hash: "${UPTIME_AUTH_PASSWORD_HASH}"
```

### 11.1 范围

始终公开：

```text
/livez
/readyz
```

当 `auth.enabled=true` 时保护：

```text
<ui.path>
<ui.path>/*
```

默认即：

```text
/uptime
/uptime/api/status
```

### 11.2 凭据

- 第一版只支持单账号；
- 不支持明文 `password` 字段；
- `password_hash` 使用 Fiber BasicAuth 支持的预哈希 verifier；
- 不做登录页面；
- 不做 Session；
- 不做 RBAC；
- 不做 OAuth / OIDC。

高级访问控制继续交给：

- Nginx；
- Caddy；
- Cloudflare Access；
- Tailscale；
- VPN；
- Private Network。

## 12. Uptime 配置

```yaml
uptime:
  interval: 10s
  retention: 90d
  window: 30d
  timezone: UTC
```

### 12.1 `interval`

Standalone 产品默认：

```text
10s
```

而不是直接复制 Fiber Uptime middleware 的更激进默认采样周期。

最低：

```text
1s
```

使用 Go duration。

### 12.2 `retention`

默认：

```text
90d
```

这是 **calendar-day span**，不是 `time.Duration`。

仅接受：

```text
Nd
```

例如：

```text
1d
30d
90d
365d
```

### 12.3 `window`

默认：

```text
30d
```

同样使用 calendar-day span。

要求：

```text
1d <= window <= retention
```

不满足时直接配置失败，不做静默裁剪。

### 12.4 `timezone`

默认：

```text
UTC
```

支持显式：

```text
Local
Asia/Tokyo
Asia/Shanghai
...
```

Timezone 决定：

- 日界线；
- slot 所属日期；
- daily rollup；
- retention；
- archive 的历史语义。

## 13. UI 配置

```yaml
ui:
  path: "/uptime"
  title: "Service Status"
  description: "Current service availability."
  footer: "Powered by DeepFurry Uptime."
  favicon_url: ""

  thresholds:
    green: 0.999
    yellow: 0.99
```

### 13.1 Path

默认：

```text
/uptime
```

API 固定跟随：

```text
<ui.path>/api/status
```

规则：

- 自动标准化前导 `/`；
- 去除多余尾部 `/`；
- 不允许 `/`；
- 不允许与 `/livez`、`/readyz` 冲突。

Auth 根据最终 `ui.path` 动态保护，不硬编码 `/uptime`。

### 13.2 Thresholds

默认：

```text
green:  0.999
yellow: 0.99
```

要求：

```text
0 < yellow <= green <= 1
```

### 13.3 Favicon

空值使用 Fiber Uptime 内置 favicon。

允许 Fiber Uptime 支持的 same-origin root-relative URL 或 absolute HTTP(S) URL。

私有部署推荐 same-origin，避免浏览器访问第三方 favicon 泄露访问行为。

## 14. Endpoint 配置

```yaml
endpoints:
  - id: api
    name: "API"
    description: "Public API"
    url: "https://api.example.com/health"
    method: GET
    interval: 10s
    timeout: 5s
    headers:
      Authorization: "Bearer ${UPTIME_API_TOKEN}"
    expected_status_codes:
      - 200
      - 204
```

### 14.1 ID

ID 是持久化身份，不是展示名称。

建议校验：

```text
^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$
```

ID：

- 必须唯一；
- 大小写敏感；
- 建议使用小写；
- 会进入 bbolt key、Redis key namespace、CLI、Archive 与日志。

修改 ID 的语义：

```text
旧 ID → detached historical service
新 ID → new service
```

`name` 与 `description` 可以随时修改，不创建新 Service。

### 14.2 URL

仅允许绝对：

```text
http://
https://
```

### 14.3 Method

v0.1.0 产品层仅允许：

```text
GET
HEAD
```

即使 Fiber Uptime 底层能够接受其他合法 HTTP method，本产品也不开放有潜在副作用的 POST / PUT / PATCH / DELETE。

默认：

```text
GET
```

### 14.4 Interval

Endpoint 未配置 `interval` 时继承：

```text
uptime.interval
```

允许 endpoint 覆盖全局 interval。

最低：

```text
1s
```

### 14.5 Timeout

默认：

```text
min(5s, effective interval)
```

显式配置要求：

```text
0 < timeout <= effective interval
```

避免一个探测持续时间长期超过调度周期。

### 14.6 Status Code

`expected_status_codes` 为空时：

```text
2xx / 3xx → UP
其他       → missed slot
```

显式配置后只接受列表中的状态码。

### 14.7 Redirect

第一版保持 Fiber Uptime 语义：

- 不主动 follow redirect；
- redirect response 本身按状态码判断；
- 默认情况下 3xx 属于 UP；
- 若只接受 200，用户显式配置 `expected_status_codes: [200]`。

### 14.8 Retry

不做 retry。

每个 interval：

```text
one probe
  ↓
success → heartbeat
failure → missed slot
```

下一 interval 自然再次尝试。

### 14.9 Initial Probe

Endpoint runtime 启动后立即进行第一次 probe，然后进入 interval ticker。

### 14.10 Header 安全

Endpoint Header：

- 可以使用 active environment interpolation；
- 不记录值；
- 不展示到 UI；
- 不进入 Archive；
- 不读取或记录 response body。

## 15. Storage 产品语义

配置：

```yaml
storage:
  type: bbolt

  bbolt:
    path: "./data/uptime.db"

  redis:
    url: "${UPTIME_REDIS_URL}"
    key_prefix: "fiber:uptime"
```

### 15.1 `type`

支持：

```text
bbolt
redis
```

默认：

```text
bbolt
```

Inactive backend 的字段不做 active env resolution，也不验证连接。

### 15.2 bbolt

默认路径：

```text
./data/uptime.db
```

行为：

- 自动创建父目录；
- 数据库文件不存在时自动创建；
- 建议目录权限 `0750`；
- 数据库文件 `0600`；
- 单实例持有文件；
- 不支持多个进程共享同一个 DB file；
- 不提供 memory fallback；
- backend 无法打开时启动失败。

### 15.3 Redis

Redis 的定位：

> Shared external persistence.

不是：

> Distributed probe scheduler / HA monitoring.

配置：

```yaml
redis:
  url: "${UPTIME_REDIS_URL}"
  key_prefix: "fiber:uptime"
```

`key_prefix` 默认：

```text
fiber:uptime
```

用于环境隔离。

多个 Uptime 实例共享 Redis 与 prefix 时：

- 可以共享持久化历史；
- 每个实例仍会独立执行 endpoint probe；
- N 个实例会产生约 N 倍 probe 流量；
- 不承诺 leader election 或 probe ownership。

## 16. Public `storage/bbolt` Package

### 16.1 为什么公开

bbolt backend 不放进：

```text
internal/storage/bbolt
```

而是公开：

```text
github.com/deepfurry/uptime/storage/bbolt
```

原因：

1. Fiber Uptime v0.2.0 已提供正式 `uptime/storage.Store` 扩展契约；
2. standalone 产品本身就是该扩展点的真实使用者；
3. 第三方 Fiber 应用可以只复用 bbolt backend，而不运行 DeepFurry standalone service；
4. 公开 package 让 upstream extensibility 与 DeepFurry 产品形成清晰闭环；
5. 不再需要旧 GoFurry prototype 的 bbolt → Redis emulation。

需单独维护：

```text
docs/design/bbolt-storage.md
```

解释这一设计背景、取舍与兼容承诺。

### 16.2 建议公开 API

```go
package bbolt

type Config struct {
    Path    string
    Timeout time.Duration
}

type Store struct {
    // private fields
}

func Open(config Config) (*Store, error)

func (s *Store) Name() string
func (s *Store) Ping(ctx context.Context) error
func (s *Store) RemoveService(ctx context.Context, serviceID string) error
func (s *Store) Close() error
```

并编译期确认：

```go
var _ uptimestorage.Store = (*Store)(nil)
```

`uptime/storage.Store` 本身不负责资源初始化和 shutdown，因此：

- `Open` 在传给 `uptime.New` 前完成；
- caller 持有 lifecycle；
- standalone 应用在 Fiber 完成 shutdown 后关闭 Store。

```text
│       └── <YYYY-MM-DD>
│           ├── up_slots
│           └── slots
│               └── <slot-key>
│
└── daily
    └── <service-id>
        └── <YYYY-MM-DD>
            ├── up_slots
            ├── expected_slots
            └── finalized
```

### 17.1 编码

不使用：

```text
JSON
Gob
Protobuf
MsgPack
```

建议：

- UTF-8 string → raw bytes；
- int64 / uint64 → 8-byte big endian；
- `time.Time` → UnixNano int64；
- `time.Duration` → nanoseconds int64；
- bool → single byte；
- instance ID key → big-endian integer；
- slot key → big-endian integer；
- day → ASCII `YYYY-MM-DD`；
- service ID → UTF-8 bytes。

### 17.2 Schema Version

从第一版即存在：

```text
meta/schema_version = 1
```

启动：

```text
new DB                    → initialize v1
version == supported      → open
version < current         → future forward migration
version > current         → refuse startup
```

v0.1.0 不建立通用 migration framework。

未来真正出现 v2 时再实现：

```text
migrateV1ToV2()
```

## 18. bbolt Store 语义

### 18.1 `UpsertService`

不变量：

```text
CreatedAt       immutable
Name            mutable
Description     mutable
SampleInterval  mutable
LastSeenAt      monotonic max
```

### 18.2 `UpsertInstance`

不变量：

```text
StartedAt       immutable
ServiceID       refreshable
Hostname        refreshable
PID             refreshable
LastSeenAt      monotonic max
```

### 18.3 `WriteHeartbeat`

Heartbeat 去重身份：

```text
(ServiceID, Day, Slot)
```

同一个 slot 重复写入只计一次。

一次 `db.Update` 原子完成：

```text
service last_seen_at = max(...)
instance last_seen_at = max(...)
insert slot if absent
increment up_slots only when slot was absent
```

`up_slots` 作为冗余计数保存，避免状态查询扫描所有 slot。

v0.1.0 使用“一 slot 一 key”，不提前引入 bitmap。

### 18.4 `RollupDaily`

- 只处理 `< BeforeDay`；
- 已 finalized 的 daily 不允许覆盖；
- `ExpectedSlots` callback 在调用周期内使用；
- 同一 Service 的 eligible days 可在短写事务内完成；
- Rollup 不负责立即删除 raw samples。

### 18.5 `Cleanup`

删除 raw sample 的前提：

```text
day < SamplesBeforeDay
AND
corresponding daily row exists
AND
daily.finalized == true
```

未 finalized 的 raw sample 必须保留。

Daily history 根据 `DailyBeforeDay` 删除。

Instance metadata 作为运行时信息，可固定保留约 24 小时并在 Cleanup 中顺带清理，不为此建立独立 background worker。

### 18.6 Query

返回尽量稳定排序：

```text
ServiceID ASC
Day ASC
```

虽然 upstream contract 不要求顺序，但 deterministic result 有利于测试、CLI 与第三方调用。

### 18.7 Context

bbolt transaction 本身不接受 `context.Context`。

实现采取 best-effort：

- transaction 前检查 `ctx.Err()`；
- 长循环周期性检查；
- 不虚构“等待 writer lock 可被 context 精确中断”的保证。

该限制必须在 bbolt 设计文档中说明。

### 18.8 `Ping`

只执行轻量 read readiness check：

- DB handle 未关闭；
- `meta` 可读；
- schema version 可读且支持。

不为了 readiness 创建临时写数据。

### 18.9 `RemoveService`

单 write transaction 删除：

```text
services/<id>
samples/<id>
daily/<id>
instances where service_id == <id>
```

不允许留下半删除状态。

## 19. Service 生命周期与 Detached 状态

### 19.1 定义

当前 YAML 中的 Endpoint ID 集合：

```text
configured services
```

Storage 中的 Service ID 集合：

```text
persisted services
```

若 persisted service 不再存在于配置：

```text
detached service
```

`active / detached` 是运行时推导状态，不保存：

```text
archived=true
active=false
```

这类数据库字段。

### 19.2 删除配置不会删历史

例如：

```text
api-v1 从 YAML 删除
        ↓
停止继续监控
        ↓
历史仍存在
        ↓
api-v1 = detached
```

第一版接受 Fiber Uptime dashboard 仍显示该 persisted service。

这既保留历史，也提醒用户需要显式处理。

不通过过滤 Store 隐藏 detached 数据。

## 20. Service Archive

### 20.1 用途

Archive 用于：

> 保留某个历史 Service 的人类可读记录。

不是：

> 数据库 backup / restore format。

### 20.2 格式

版本化 JSON，例如：

```json
{
  "format": "deepfurry-uptime-service-archive",
  "version": 1,
  "application_version": "0.1.0",
  "exported_at": "2026-09-16T12:30:00Z",
  "timezone": "Asia/Tokyo",
  "service": {
    "id": "api-v1",
    "name": "API v1",
    "description": "Legacy API",
    "created_at": "...",
    "last_seen_at": "...",
    "sample_interval": "10s"
  },
  "daily": [],
  "current_day": {
    "day": "2026-09-16",
    "up_slots": 0,
    "expected_slots_so_far": 0
  }
}
```

Archive 不包含：

- BasicAuth 信息；
- Endpoint request headers；
- Redis credential；
- process instance ID；
- PID；
- hostname；
- raw slot records。

### 20.3 Export 层次

Export 是 storage-independent application capability。

通过公开 Store 查询能力组合数据，而不是做：

```text
bbolt-specific export
redis-specific export
```

### 20.4 Import

v0.1.0 不支持 Archive import。

真正灾难恢复使用 backend backup。

## 21. 健康接口

### 21.1 `/livez`

语义：

> Uptime HTTP process is alive.

返回：

```text
200
ok
```

不检查被监控 Endpoint。

### 21.2 `/readyz`

语义：

> Uptime 已进入 ready lifecycle，且 active persistence backend 当前可访问。

返回：

```text
200 ready
503 not ready
```

不返回底层错误原因。

### 21.3 关键原则

即使：

```text
所有被监控 Endpoint 都 DOWN
```

仍然：

```text
/livez  = 200
/readyz = 200
```

Endpoint 故障属于监控数据，不属于 Uptime 应用自身 readiness。

### 21.4 Backend Check

bbolt：

- lightweight read/schema check。

Redis：

- 使用短 context（建议约 1s）进行 Ping。

Readiness 是 connectivity/readability signal，不承诺下一次所有写操作必然成功。

## 22. Lifecycle

### 22.1 Bootstrap

推荐顺序：

```text
1. parse CLI
2. read strict YAML
3. resolve active env values
4. validate config
5. initialize selected storage
6. preflight storage readiness
7. create Fiber app
8. register /livez and /readyz
9. register our OnPreShutdown readiness hook
10. register optional BasicAuth
11. construct Fiber Uptime middleware
12. register middleware/routes
13. register OnListen
14. register OnPostShutdown storage close
15. install signal trigger
16. app.Listen(...)
```

### 22.2 Fiber Hooks

`OnListen`：

```text
ready = true
log listening
```

`OnPreShutdown`：

```text
ready = false
```

Fiber Uptime 自己的 `OnPreShutdown`：

```text
cancel probe runtime
wait record loops
```

`OnPostShutdown`：

```text
close caller-owned bbolt / Redis resource
log shutdown result
```

### 22.3 Signal

SIGINT / SIGTERM 只触发：

```text
app.ShutdownWithTimeout(...)
```

Signal handler 不：

- 直接关闭 storage；
- 直接关闭 probe；
- 自己管理 ready；
- 自己复制 Fiber shutdown 行为。

### 22.4 Bootstrap Cleanup Safety

如果 storage 已打开但 Fiber 尚未进入完整 lifecycle 就发生后续 fatal error，需要 top-level safety cleanup。

Store `Close` 应实现幂等语义（如 `sync.Once`），因此：

```text
normal OnPostShutdown close
+
top-level defer safety close
```

不会产生重复关闭问题。

## 23. 错误与恢复语义

### 23.1 Fatal at boot

以下错误拒绝启动并 non-zero exit：

- CLI 用法错误；
- YAML parse error；
- unknown config field；
- active env 缺失；
- config validation error；
- invalid timezone；
- active TLS cert/key 不可用；
- bbolt 无法打开；
- bbolt schema 不兼容；
- Redis preflight 无法连接或认证；
- listen/bind failure。

### 23.2 Runtime degraded

应用已经成功进入 ready 后：

- Redis 暂时断线；
- storage operation failure；
- bbolt I/O error；
- snapshot refresh failure

不直接 `os.Exit`。

行为：

```text
process stays alive
/livez remains 200
/readyz becomes 503 when backend check fails
Fiber Uptime reports degraded where possible
last good snapshot may continue serving
later operations naturally retry
```

Storage 恢复后 readiness 自动恢复。

### 23.3 Probe failure

以下都是正常监控结果：

- connection refused；
- timeout；
- unexpected status code；
- DNS/HTTP client failure。

结果：

```text
missed slot
```

不改变 `/readyz`。

默认不为每一个 probe failure 打 Error 日志，避免目标服务宕机时制造日志风暴。

### 23.4 Logging Guidance

建议：

```text
probe failure                  Debug / normally silent
storage operation failure      Error
storage recovery               Info
invalid config                 Error + exit
TLS/listen startup failure     Error + exit
startup/shutdown               Info
detached service detected      Info/Warning
```

日志使用 Fiber Log，默认 stdout/stderr。

不提供日志文件轮转能力。

```text
optional export
```

## 26. bbolt 维护命令与在线状态

bbolt 有独占文件锁，因此 v0.1.0 明确规定：

```text
service list/export/remove on bbolt
→ offline maintenance
```

操作流程：

```text
stop uptime
run maintenance command
start uptime
```

不为了在线维护新增：

- admin HTTP API；
- Unix socket control plane；
- IPC；
- second process coordination。

Redis 是外置 persistence，`service list/export/remove` 可以在线执行，但 active service 删除限制仍然有效。

## 27. Backup 与 Archive 区分

### 27.1 Archive

对象：

```text
single service history
```

目标：

```text
human-readable historical record
```

格式：

```text
versioned JSON
```

不可用于 DB restore。

### 27.2 bbolt Backup

v0.1.0 推荐 cold backup：

```text
graceful stop
copy uptime.db
start
```

不建议运行中直接普通 `cp` 并假设一致性。

未来若有明确需求，再基于 bbolt consistent transaction backup 设计在线备份能力。

### 27.3 Redis Backup

使用 Redis 原生：

- RDB；
- AOF；
- 云服务备份；
- 用户现有灾备方案。

DeepFurry Uptime 不重复实现 Redis backup system。

- 非特权端口；

## 32. 安全边界

### 32.1 默认公开不等于默认安全暴露

`auth.enabled=false` 是为了支持公开 status page、VPN、Zero Trust、reverse proxy 等场景。

文档必须提示：

- Uptime history 可能暴露内部服务名称与运维规律；
- 敏感环境应启用 BasicAuth 或外部访问控制；
- 直接公网部署建议使用 TLS。

### 32.2 Secrets

严禁日志或导出：

- password verifier；
- Redis credential；
- Authorization Header；
- Cookie；
- query string 中人为放置的 secrets；
- response body。

Endpoint URL 本身可能被上游网络设备记录，因此文档应明确：

> 不要把 secret 放在 URL 中。

### 32.3 TLS

TLS 开启后失败绝不 downgrade 到 HTTP。

### 32.4 Health Endpoint

`/livez`、`/readyz` 永远公开，但只返回固定最小文本，不返回：

- DB path；
- Redis address；
- error stack；
- endpoint topology；
- credential；
- internal configuration。

## 33. v0.1.0 验收标准

v0.1.0 可以发布的最低条件：

9. `/livez` 与 `/readyz` 语义正确。

## 35. 最终产品原则摘要

DeepFurry Uptime v0.1.0 应始终满足以下判断：

```text
Fiber-native
Small
Explicit
Predictable
Zero-infrastructure by default
Configuration-driven
History-safe
Operationally boring
```

当一个新功能需要引入新的控制面、后台系统、常驻 worker、额外数据库、复杂分布式协议或大量依赖时，默认答案应是“不进入当前产品边界”，除非真实用户需求足以证明其必要性。

产品最终希望解决的不是：

> “如何做一个功能最多的监控平台？”

而是：

> “如何让一个只想知道几个 HTTP 服务是否稳定的人，用一个 binary 和一份 YAML，就得到可靠、持久、可维护的 Uptime 服务？”
